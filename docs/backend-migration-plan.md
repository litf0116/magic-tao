# Magic-Tao 后端迁移计划

> **目标**：将后端从 .NET 8 + ABP Framework 逐步迁移到 Spring Boot (Java)，最终统一技术栈
> **方式**：绞杀藤模式（Strangler Fig）—— 新功能直接写 Java，老模块逐个替换
> **原则**：不搞大爆炸，保证业务连续性，每个迁移步骤都有回退能力

---

## 一、迁移总纲

### 1.1 为什么迁

| 维度 | 现状 | 目标 |
|------|------|------|
| 技术栈 | C# .NET 8 + ABP Framework | Java (Spring Boot) |
| 团队能力 | 一人兼职，Java 主栈（C# 仅能靠 AI 辅助修改） | 统一技术栈，脱离 AI 也能独立维护 |
| 系统归属权 | **AI 不在就改不了代码**——语法不熟，无法手写 C# | **自己能改**——Java 是自身掌握的语言，AI 只是提速工具 |
| AI 辅助效率 | ABP 生态 AI 训练数据少，排错成本高 | Java 生态 AI 支持最成熟 |
| 新功能开发 | 在老栈上加新代码 → 未来又多一份迁移成本 | 新功能直接写 Java，逐步吃掉老系统 |

> **核心逻辑**：当前系统的维护能力完全依赖于 AI 工具。AI 在 → 能干活。AI 不在 → 动不了。迁移到 Java 的本质不是"换技术栈"，而是**把系统控制权从"AI + 你"变成"你 + AI"**——后者你说了算，前者 AI 说了算。你自己能改，才是你的系统。

### 1.2 核心策略：绞杀藤模式

```
不做什么：
  ❌ 停掉 .NET 服务，等 Java 全写好了再上线
  ❌ 一次性迁移所有表结构
  ❌ 大爆炸切换

做什么：
  ✅ 新功能直接写 Java，不走 .NET
  ✅ 老模块逐个在 Java 端重写，每个模块独立切换
  ✅ Nginx 按路由分流，前端无感知
  ✅ API 重新设计（RESTful），3 个前端端同步改
```

### 1.3 迁移期间系统架构

```
                    Nginx (www.molitao.top)
                          │
               ┌──────────┴──────────┐
               │                     │
          Spring Boot           .NET ABP
      (新功能 + 已迁移模块)    (未迁移老模块)
               │                     │
               └──────────┬──────────┘
                          │
                     同一数据库 (MySQL)


  ── 共享 JWT Secret：两个系统都能验证同一份 token
  ── 共库操作：两个系统读写同一张表，不存在"数据同步"环节
  ── 事务边界：各自事务在各自系统内完成，不跨系统分布式事务
```

## 二、模块迁移优先级

迁移分 3 个梯队，**P0 最独立→P2 最复杂**，每搬完一个梯队降低一份风险。

### 梯队划分

| 梯队 | 模块 | 理由 | 预估工期 |
|------|------|------|---------|
| **P0** | CMS / 公告 | 数据独立，无事务耦合，最简单 | 2-3 周/模块 |
| **P0** | 广告 / Banner | 同上 | 1-2 周 |
| **P0** | 系统配置 | 读写分离，逻辑简单 | 1 周 |
| **P1** | 用户注册登录 | 涉及 JWT 共享，需注意兼容 | 2-3 周 |
| **P1** | 角色权限 | 跟陕量的权限系统互相借鉴 | 2-3 周 |
| **P1** | 短信通知 | 外部 SDK 对接，逻辑独立 | 1-2 周 |
| **P2** | 拍卖业务 | 事务链最长，出价/竞拍/成交逻辑复杂 | 4-6 周 |
| **P2** | 支付 | 微信回调 URL 固定，需要特殊处理 | 2-3 周 |
| **P2** | FreeIM 消息 | 实时通信，最复杂的外部集成 | 4-6 周 |

### 迁移顺序约束

```
P0 (独立简单) ──先做，获得信心──→ P1 (用户权限) ──核心能力──→ P2 (复杂业务)
     │                                │                           │
     └── CMS/公告/配置广告              ├── 用户/角色/权限           ├── 拍卖
                                       ├── 短信/内容安全           ├── 支付
                                       └── 内容审核               └── FreeIM
```

## 三、迁移流程规范

### 3.1 模块迁移 5 步法

每个模块严格按以下步骤执行：

```
Step 1: Java 端实现
├── 在 Java 端编写该模块的全部接口（业务逻辑透明翻译，不改动）
├── 设计新的 RESTful API（参考第四章 API 设计规范）
├── 直接读写同一张 MySQL 表
└── 单元测试覆盖核心逻辑

Step 2: 并行验证
├── Nginx 添加新路由，Java 端接口上线
├── 手动调用 Java 接口，验证返回数据与 .NET 接口一致
├── 走一遍核心业务场景（增删改查）
└── 修复发现的差异

Step 3: 前端改造
├── PC (Vue3)、UniApp、Flutter 三端同步修改为该模块的新 API
├── 开发环境联调通过
└── 提交代码

Step 4: 上线切换
├── 新前端 + Spring Boot 同一天部署上线
├── Nginx 将对应路由切到 Java 端
├── 冒烟测试核心流程
└── 观察 3 天线上日志

Step 5: 关闭旧代码
├── 确认 Java 端运行正常（无错误日志、无功能异常）
├── .NET 端该模块代码不再维护（不删除，保留回退能力）
└── 更新迁移进度表
```

### 3.2 安全门条件

每个模块在 Step 4 切换上线前，必须满足以下所有条件：

```
┌─ 安全门 Checklist ──────────────────────────────────────┐
│  □ 1. Java 接口已通过测试，核心流程无 bug                │
│  □ 2. API 响应格式与约定一致（见第四章）                  │
│  □ 3. 3 个前端端均已改造完成，联调通过                    │
│  □ 4. Nginx 路由配置已就绪                               │
│  □ 5. 回退方案就绪：保留 .NET 服务，Nginx 可一秒切回       │
│  □ 6. 观察期：上线后连续 3 天无功能异常（高峰期至少覆盖 1 天）│
└──────────────────────────────────────────────────────────┘
```

### 3.3 回退流程

一旦上线后发现严重问题（业务中断、数据错误），立即执行回退：

```
触发回退条件：
├── 业务功能不可用（返回 500 错误率 > 1%）
├── 数据写入错误（金额/状态字段不正确）
└── 用户反馈核心流程不通

回退步骤：
1. Nginx 将该模块路由切回 .NET
2. 前端回滚到上一版本
3. 确认旧链路业务正常
4. 记录问题，修复后重新走迁移流程
```

## 四、API 设计规范

### 4.1 新 API 风格

迁移后的新后端统一使用 RESTful 风格：

```
旧 (ABP 约定路由)          新 (Spring Boot RESTful)
──────────────────────────────────────────────────
POST /api/services/app/Article/Create
                          → POST   /api/v1/articles
GET /api/services/app/Article/Get?id=1
                          → GET    /api/v1/articles/1
PUT /api/services/app/Article/Update
                          → PUT    /api/v1/articles/1
DELETE /api/services/app/Article/Delete?id=1
                          → DELETE /api/v1/articles/1
GET /api/services/app/Article/GetAll?page=1&limit=20
                          → GET    /api/v1/articles?page=1&limit=20

GET /api/services/app/AuctionRecord/GetList
                          → GET    /api/v1/auction-records
```

### 4.2 统一响应格式

```json
// 成功
{
  "code": 0,
  "message": "success",
  "data": { ... }
}

// 失败
{
  "code": 40001,
  "message": "参数错误：xxx 不能为空",
  "data": null
}

// 分页
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [...],
    "total": 100,
    "page": 1,
    "limit": 20
  }
}
```

### 4.3 HTTP 状态码使用规范

| 场景 | HTTP Status | business code |
|------|-------------|---------------|
| 正常返回 | 200 | 0 |
| 请求参数错误 | 400 | 40001+ |
| 未登录 | 401 | 40100 |
| 无权限 | 403 | 40300 |
| 资源不存在 | 404 | 40400 |
| 业务逻辑错误 | 409 | 40901+ |
| 服务端错误 | 500 | 50000 |

### 4.4 例外：微信支付回调

微信支付回调 URL 在商户平台配置，更改成本高。处理方式：

```
方案：在 Spring Boot 中暴露与 ABP 旧路径一致的接口
  旧路径：/api/services/app/Payment/WechatPayNotify
  新路径：/api/v1/payments/wechat/notify

Nginx 配置：
  location = /api/services/app/Payment/WechatPayNotify {
      proxy_pass http://spring-boot;  # 直接转发到 Java 端
  }

说明：仅此一个接口保留旧路径，内部逻辑使用 Java 新实现。
      其余支付相关接口（查询/退款等）走新 RESTful 风格。
```

## 五、新老系统共存规则

### 5.1 数据库规则

```
1. Java 端读数据：直接读 MySQL 表，不走 .NET 接口
2. Java 端写数据：直接写 MySQL 表
   → 注意：ABP 的审计字段（CreationTime/CreatorId/LastModificationTime）
     需要 Java 端手动维护
3. 实体主键：保持跟现有数据库一致（long/auto increment）
4. 不允许跨服务分布式事务
   → 如果一个操作涉及 Java + .NET 两侧的数据，拆成独立操作
   → 或用补偿逻辑处理（先写 Java 端，再 HTTP 调 .NET 端）
```

### 5.2 JWT 共享规则

```
1. 两个系统使用同一个 JWT Secret
2. 登录接口可以放在任意一端，产生的 token 两端都能验证
3. token 的 claims 结构保持一致（userId, userName, roles）
4. 如果改动了 JWT 配置，两端同步更新
```

### 5.3 服务间调用规则

```
必须跨服务调用时：
├── 走 HTTP（RestTemplate / WebClient），不引入消息队列
├── 设置合理的超时时间（默认 3 秒）
├── 做好熔断/降级（调用失败不影响主流程）
└── 尽量避免循环调用（A 调 B，B 又调 A）
```

## 六、新功能开发规范

### 6.1 开发决策矩阵

开始一个新功能前，按此规则决策：

```
                        ┌──────────────────────┐
                        │ 新功能还是改老功能？    │
                        └──────────┬───────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
          全新功能             改老模块             修 Bug
              │                    │                    │
              ▼                    │                    ▼
       直接写 Java                 │              在 .NET 里修
                                   │                    │
                    ┌──────────────┴──────────────┐     │
                    ▼                             ▼     │
              改动小                         改动大      │
                    │                             │      │
                    ▼                             ▼      │
            在 .NET 里改               在 Java 端重写     │
                                      这个模块            │
                                                        │
                                        ┌────────────────┘
                                        ▼
                                   上线运行，迁移完成
```

### 6.2 新功能技术栈选型

```
├── Spring Boot 3.x + JDK 17/21
├── MyBatis-Plus（ORM，对标 EF Core）
├── Spring Security（对标 ABP 权限）
├── Redis（缓存，现有基础设施不变）
├── MySQL 8.0（数据库不变）
└── 构建工具：Maven（推荐）或 Gradle
```

## 九、注意事项

1. **不重构只翻译**——Java 端只重写逻辑，不优化表结构、不改业务规则。优化是迁移完成之后的事，分开进行。
2. **每写一个新功能先想：能不能直接写 Java？**——如果答案是"能"，就不要再往 .NET 里加新代码。
3. **保留回退能力**——.NET 服务不删， Nginx 配置保留旧路由。万一 Java 端出问题，一键切回。
4. **不影响业务方交付节奏**——每月都有 Java 端的新功能上线，业务方看到的是持续交付，而不是"他们在重构"。
5. **API 向后兼容**——如果外部调用方（微信回调等）绑定了旧 URL，保留兼容路由或 Nginx 重写。
6. **日志和监控统一**——Java 端和 .NET 端的日志聚合到同一处（Elasticsearch 或文件），便于排错时串联请求。
